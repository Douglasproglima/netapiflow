# Performance report for NetApiFlow 0.6.0

Measured on 2026-11-25 with `tests/NetApiFlow.Benchmarks` (BenchmarkDotNet 0.15.8). The numbers in the README come from this report.

## What was measured, and on what

| | |
|---|---|
| NetApiFlow source | `src/` of `develop` at `65b3c06`. It is unchanged in every later commit up to the one that adds this report. |
| Benchmark harness | commit `7f48efb` of this branch |
| Baseline for `Flow.Step` | the published `0.5.3` package from nuget.org, run with the same source files |
| Hardware | 12th Gen Intel Core i7-1255U 1.70 GHz, 1 CPU, 10 physical and 12 logical cores, about 40 GB of RAM. A laptop, on AC power, power plan High performance. |
| Operating system | Windows 10 Home 22H2 (10.0.19045.6466) |
| Runtimes | .NET 8.0.34 and .NET 10.0.15, X64 RyuJIT x86-64-v3. SDK 10.0.404. |

The machine was not idle. Visual Studio, Chrome and other programs were open, and other coding sessions were building and testing on it. CPU load sampled before and during the runs ranged from 18% to 96%. That is why most cells give a median and a range, and why the `Flow.Step` comparison alternates the two versions round by round. Read the numbers as an order of magnitude, not as a lab result.

## How it is measured

- Requests go through `TestServer.SendAsync`, which runs the real middleware pipeline without sockets. A real `HttpClient` would add jitter larger than the few microseconds being measured.
- Logging providers are cleared. The default console provider writes on every request and that I/O dwarfs the difference.
- Each scenario is its own class and BenchmarkDotNet runs each class in its own process. The `ActivitySource` listener that `AddNetApiFlow` registers is process-wide, so an "absent" run in the same process as an "enabled" one would be wrong.
- `Simple` is one endpoint with no marked step. `Nested` has four nested `Flow.Step` calls (controller, service, repository, database). `NestedConcurrent` sends 16 `Nested` requests at the same time, and the time shown is per request.
- `[MemoryDiagnoser]` is on, so every row also has the allocation per operation.
- `Flow.Step` is measured in two ways, 250 sequential steps per call (under the limit of 300 spans per trace), reported per step: outside any request, and inside a request that is being traced.

Tracing with default options adds 12.8 μs to `Simple` and 22.6 μs to `Nested` (Enabled minus Absent, medians). With `Enabled = false` the additions are 1.0 μs and 1.7 μs.

### net10.0

| Scenario | Simple | Nested, 4 steps | Nested, 16 at a time (per request) | Allocated, Simple and Nested |
|---|---|---|---|---|
| Absent | 5.4 (5.1 to 5.7) | 7.4 (7.2 to 7.7) | 4.4 (3.9 to 4.8) | 5.85 KB and 6.21 KB |
| Disabled | 5.9 (5.8 to 6.0) | 7.8 (7.6 to 7.9) | 3.7 (3.2 to 4.2) | 5.9 KB and 6.38 KB |

The old README said tracing cost "about 32 μs more with four nested steps". That was wrong. 32 μs was the whole overhead of the `Nested` scenario in the first measurement (43.84 μs with tracing against 11.79 μs without), not an increase on top of the `Simple` one.

## `Flow.Step` against the published 0.5.3

Mean time per step in nanoseconds, median of the rounds with the smallest and largest round in brackets. The published package and the current code run the same benchmark source, one after the other, round after round, so that a change in machine load hits both. "Higher" counts the rounds in which the current code was slower than 0.5.3 in the same round.

### net8.0

| Case | 0.5.3 | Current | Difference of medians | Rounds with current higher | Allocated per step, 0.5.3 and current |
|---|---|---|---|---|---|
| Enabled = true, inside a request | 278.1 (244.4 to 324.3), 8 rounds | 324.8 (264.4 to 518.7), 8 rounds | +46.8 ns (+17%) | 8 of 8 | 350 B and 353 B |
| Enabled = true, outside any request | 144.1 (130.3 to 172.2), 8 rounds | 143.9 (136.1 to 227.8), 8 rounds | -0.2 ns (0%) | 3 of 8 | 320 B and 320 B |
| Enabled = false, inside a request | 162.0 (159.6 to 165.8), 3 rounds | 28.1 (24.7 to 29.7), 3 rounds | -133.9 ns (-83%) | 0 of 3 | 256 B and 24 B |
| Enabled = false, outside any request | 84.3 (82.2 to 86.5), 3 rounds | 0.5 (0.5 to 0.5), 3 rounds | -83.8 ns (-99%) | 0 of 3 | 232 B and 0 B |

### net10.0

| Case | 0.5.3 | Current | Difference of medians | Rounds with current higher | Allocated per step, 0.5.3 and current |
|---|---|---|---|---|---|
| Enabled = true, inside a request | 231.4 (174.8 to 508.4), 8 rounds | 246.5 (196.7 to 251.6), 8 rounds | +15.1 ns (+7%) | 4 of 8 | 349 B and 352 B |
| Enabled = true, outside any request | 95.8 (86.3 to 233.4), 8 rounds | 86.5 (80.4 to 104.4), 8 rounds | -9.3 ns (-10%) | 1 of 8 | 320 B and 320 B |
| Enabled = false, inside a request | 155.1 (130.0 to 355.7), 3 rounds | 20.0 (19.8 to 24.2), 3 rounds | -135.1 ns (-87%) | 0 of 3 | 256 B and 24 B |
| Enabled = false, outside any request | 67.6 (56.3 to 78.9), 3 rounds | 0.5 (0.5 to 0.6), 3 rounds | -67.0 ns (-99%) | 0 of 3 | 232 B and 0 B |

What the numbers say:

- `Enabled = false` is much cheaper than in 0.5.3. A step outside a request costs about 0.5 ns and allocates nothing, against 68 to 84 ns and 232 bytes in 0.5.3. Inside a request the step costs 20 to 28 ns against 155 to 162 ns. The ranges of the two versions do not touch.
- `Enabled = true` outside any request is no slower than 0.5.3: the same on .NET 8, and about 9 ns cheaper on .NET 10.
- `Enabled = true` inside a request, on .NET 8: the current code was slower in 8 of 8 rounds, and the median round-by-round difference was +41 ns per step, about 15%. Even the smallest difference was +12 ns. With 250 steps in one request, +41 ns per step is about 10 μs per request.
- `Enabled = true` inside a request, on .NET 10: the current code was slower in 4 of 8 rounds, and the median round-by-round difference was +9 ns. The ranges overlap, and the best round of each version differs by +22 ns. This one is inside the noise of this machine.
- The allocation per step is the same, 349 to 350 bytes in 0.5.3 and 352 to 353 bytes now.

Nothing here says where the extra time of an enabled step comes from. It was not looked for. The two `Volatile.Read` calls that `Flow.Step` now does before it asks for listeners are not the cause: the disabled path, which pays for them too, got cheaper.

## What this does not show

- Two rounds per .NET version for the request table is not much, and the cells span a wide range. A quiet machine would give tighter numbers.
- One machine, one operating system, one CPU. The ratio between scenarios is more portable than the absolute microseconds.
- A request with a real network stack, a real database or a real serializer costs far more than any row here, so the overhead of tracing is a small share of it.

## How to reproduce

From the repository root, once per .NET version (`net8.0` and `net10.0`):

```bash
cd tests/NetApiFlow.Benchmarks
dotnet run -c Release -f net10.0 -- --filter 'NetApiFlow.Benchmarks.AbsentOverheadBenchmarks*' 'NetApiFlow.Benchmarks.DisabledOverheadBenchmarks*' 'NetApiFlow.Benchmarks.EnabledOverheadBenchmarks*'
dotnet run -c Release -f net10.0 -- --filter 'NetApiFlow.Benchmarks.Step*'

cd ../manual-verification/Fase59DesempenhoVerification
dotnet run -c Release -f net10.0 -- --filter 'NetApiFlow.Benchmarks.Step*'
```

The second folder builds the same step benchmarks against the published `NetApiFlow` 0.5.3 package (it calls `NetApiFlow.Step`, the name that `Flow.Step` had then). Run the two step commands one after the other, several times, and compare round by round. BenchmarkDotNet writes its own reports under `BenchmarkDotNet.Artifacts/results/` in the folder where it runs.

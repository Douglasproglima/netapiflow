# Replay play button clipped on short desktop viewports

Proves and fixes a real bug reported live by the project owner on a 1080p monitor: with a
replay active, the replay bar's play button (`.flow-workspace__replay-play`) could be clipped
out of view, or genuinely unclickable, whenever the browser's usable content height was short
enough. No automated test in `NetApiFlow.slnx` covers viewport height, so this has to be proven
by hand against a real running dashboard.

## Root cause

`.flow-workspace__center` (the graph card) is `display: flex; flex-direction: column;
overflow: hidden`. Its children are the toolbar, the graph header, the optional banner, the
canvas (`flex: 1 1 auto; min-height: 200px`) and, when replaying, the replay bar (`flex: none`).

When the card's allocated height is shorter than toolbar + header + banner + the canvas's
200px floor + the replay bar's own height combined, the canvas cannot shrink past its floor, so
the column overflows. Since the card clips with `overflow: hidden`, the replay bar, the last
item in that column, is the one that gets cut off.

## Reproducing it (before the fix)

1. `samples/SampleApi.Controllers` running locally (`ASPNETCORE_ENVIRONMENT=Development`, a real
   Postgres reachable via the configured connection string), a real trace generated by calling
   `GET /api/orders/1/slow`, opened at `/flow?trace=<id>`.
2. Browser viewport resized to `1920x870`, the CSS-pixel budget a real 1080p monitor leaves for
   page content once the OS taskbar and the browser's own tabs/address bar/bookmarks bar are
   subtracted.
3. Replay started via the "Replay" button in the graph header.
4. Checked two ways, not just visually:
   - `getBoundingClientRect()` of the play button against `.flow-workspace__center`.
   - `document.elementFromPoint()` at the play button's own center point.

Result, before the fix:

```json
{
  "viewport": { "w": 1920, "h": 870 },
  "btnRect": { "top": 664, "bottom": 704 },
  "centerRect": { "top": 280, "bottom": 618 },
  "overflowPastBy": 86,
  "elementAtButtonCenter": "<div class=\"recent-executions__header\">...",
  "elementAtButtonCenterIsButton": false
}
```

The button's own box ends 86px past the card's bottom edge: the card's `overflow: hidden` clips
it away entirely (see `before-1920x870.png`, no replay bar visible at all). A click at the
button's nominal position does not land on the button either: it lands on the "Recent
executions" header rendered below, because that is what is actually painted at that screen
position once the button itself stops being rendered there. This confirms the clip, not a
z-index overlap: nothing is drawn on top of the button, the button itself is simply cut off by
its own clipped ancestor.

## The fix

`.flow-workspace__replay` moved out of the part of the card that clips. A new wrapper,
`.flow-workspace__graph-area` (`flex: 1 1 auto; min-height: 0; overflow: hidden`), now holds the
toolbar, header, banner and canvas. The replay bar stays a direct child of
`.flow-workspace__center`, as a `flex: none` sibling of that wrapper.

A `flex: none` sibling always gets its full height from the column before a `flex: 1 1 auto;
min-height: 0` sibling does. So the replay bar reserves its own space first, and the graph area
shrinks (even past its canvas's 200px floor, since that floor now only bounds the graph area's
own content, not the whole card) to fit whatever is left. The card's own `overflow: hidden` is
unchanged, since nothing inside it needs to exceed its height anymore.

Same two checks, same viewport, after the fix:

```json
{
  "viewport": { "w": 1920, "h": 870 },
  "btnRect": { "top": 541, "bottom": 581 },
  "centerRect": { "top": 280, "bottom": 618 },
  "marginBelowCenterBottom": 37,
  "elementAtButtonCenter": "<path d=\"M8 5.5v13l10.5-6.5Z\" fill=\"currentColor\"></path>",
  "elementAtButtonCenterIsButton": true
}
```

The button is fully inside the card (37px to spare) and a click at its center hits the play
icon's own `<path>`. See `after-1920x870.png` and `after-1920x870-light.png` (dark and light
theme).

## Real monitors on this machine

The project owner reproduced the bug live on a real 1080p monitor, so the fix was also checked
against the exact resolutions of the three monitors connected to the machine this hotfix was
built on (`[System.Windows.Forms.Screen]::AllScreens`, not just the 1920x870 approximation
above):

| Monitor | Resolution | Play button top/bottom | Center card bottom | Click lands on the button |
|---|---|---|---|---|
| 1 | 1366x768 | 439 / 479 | 516 | yes |
| 2 (primary) | 2048x864 | 535 / 575 | 612 | yes |
| 3 | 1920x1080 | 751 / 791 | 828 | yes |

All three: the button's box stays inside the card, and `elementFromPoint` at the button's
center resolves to the button itself.

## Regression checks (no replay-bar change expected, confirmed unchanged)

- Desktop without a height squeeze (`1920x1080`, well above the threshold that triggers any
  shrinking): graph area keeps its full canvas, replay bar unaffected.
- Mobile width `390x844`, dark theme (`mobile-390x844-dark.png`): the page scrolls vertically at
  this breakpoint already (`.flow-workspace__body` becomes `flex-direction: column; height:
  auto` below 1024px), same as before the fix. The play button sits below the fold until
  scrolled into view, same as it always did; once scrolled to, `elementFromPoint` resolves to
  the button.
- Light theme at `1920x870` (`after-1920x870-light.png`): same layout, same result as dark.
- Action drawer open (`<1600px` width, the drawer breakpoint): the drawer is a `position: fixed`
  overlay (`z-index: 40`) with its own scrim, deliberately covering the graph card while open.
  `elementFromPoint` at the play button's position resolves to
  `endpoint-form__list-wrapper`, the drawer's own content, which is the intended modal
  behavior, unrelated to this fix. Confirmed `document.documentElement.scrollWidth <=
  window.innerWidth` at this width too: no horizontal overflow introduced.

## Impeccable

`npx impeccable detect` in URL-scan mode times out navigating to any `/flow` screen of this
sample in this environment (`Error: Navigation timeout of 30000 ms exceeded`), including
screens this change never touched (`/flow/history`). Isolated the cause: Puppeteer's Chromium
reaches a trivial local static server fine, so it is not a loopback/sandbox restriction; the
dashboard's own "Eventos ao vivo" panel keeps a persistent SSE connection open for the whole
session, which stops the page from ever reaching the network-idle state `impeccable detect`
waits for before it gives up. This reproduces on every `/flow*` URL, not just the one this fix
touches, so it is an existing gap, not something this change introduced; see the hotfix report
for what this means for `.github/workflows/ci.yml`'s own Impeccable step.

Used static file-mode detection instead (`npx impeccable detect <file> <file>`, no browser
navigation involved) against `flow-page.component.html` and `flow-page.component.scss`:

| | Before | After |
|---|---|---|
| Findings | 0 | 0 |

No `low-contrast` or `undersized-ui-text` finding, before or after. No new finding of any kind.
